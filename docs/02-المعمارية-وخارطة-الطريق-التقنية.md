# «ممر» — المعمارية التقنية وخارطة التنفيذ

هذا المستند يصف كيف تتحول الفكرة في `01-الفكرة-والجدوى.md` إلى نظام قابل للبناء. النموذج الحيّ في `app/` ينفّذ **النواة الدنيا** من هذه المعمارية بلا أي تبعيات خارجية (Python 3 + متصفح)، ليكون مرجعاً سلوكياً للمنتج قبل اختيار التقنيات النهائية.

---

## 1. مبدأ معماري واحد

> **كل شيء «وعد» (Promise) يُسجَّل قبل أن يصبح «حدثاً» (Event)، وكل حدث يُكتب مرة واحدة في سجل غير قابل للتعديل.**

الحجز ليس «دوراً في طابور» بل **عقد كمية/زمن**، والمضخة لا تضخ إلا إذا وُجد وعد صالح، والفاتورة لا تُصدر إلا من حدث تعبئة مُثبّت. هذا المبدأ وحده يمنع بيع كميات غير موجودة، ويمنع التسريب، ويجعل التسوية اليومية حسابية لا تقديرية.

## 2. الطبقات

```
┌──────────────────────────────────────────────────────────────────┐
│  واجهات                                                          │
│  • تطبيق السائق (PWA عربي/تركي، offline-first، SMS/USSD بديل)      │
│  • لوحة المشغّل (تابلت عند المسارات)                              │
│  • لوحة المالك / BI + محاكي الجدوى                                │
│  • بوابة شركات النقل (عقود، محفظة، فواتير، API)                    │
├──────────────────────────────────────────────────────────────────┤
│  طبقة الواجهات البرمجية (API Gateway + Auth/RBAC + Idempotency)    │
├──────────────────────────────────────────────────────────────────┤
│  خدمات النطاق (Domain Services)                                   │
│  Booking • QuotaEngine • SlotScheduler • QueueOrchestrator         │
│  Wallet/Ledger • PriceBulletin • SupplyAdapter • Forecast          │
│  EventLog • Reconciliation • Notification                          │
├──────────────────────────────────────────────────────────────────┤
│  التكاملات (كلها خلف Adapters قابلة للاستبدال)                    │
│  • منصة التوريد المعتمدة (سادكوب/محروقات)  • نظام مواعيد العبور    │
│  • قياس الخزانات ATG / عدّادات المضخات     • ANPR (قراءة اللوحة)   │
│  • بوابات الدفع / الحوالات                 • الفوترة الإلكترونية    │
├──────────────────────────────────────────────────────────────────┤
│  البيانات: PostgreSQL (OLTP) + Redis (أقفال/طوابير) + Event Store  │
│  + Object Store للإيصالات + Warehouse للتحليلات                   │
└──────────────────────────────────────────────────────────────────┘
```

**قاعدة ذهبية:** `SupplyAdapter` و `BorderAdapter` معزولان تماماً. في المرحلة 1 يعملان يدوياً/شبه آلي (CSV + RPA + إدخال موظف)، وفي المرحلة 3 يستبدلان بتكامل رسمي **دون تغيير سطر واحد في خدمات النطاق**. هذا ما يجعل المشروع قابلاً للبدء غداً بدل انتظار موافقات التكامل.

## 3. نموذج البيانات (مبسّط)

| الكيان | الحقول الجوهرية | ملاحظة |
|---|---|---|
| `station` | id, name, border_id, lanes[] | منفذ السلامة = العقدة 001 |
| `product` | id, name, unit, grade | مازوت أول/إنتاجي، بنزين 90/95 |
| `price_bulletin` | id, product_id, price, currency, effective_at, source_ref | **يُثبَّت مرجعها على الحجز** |
| `tank` | id, station, product, capacity_l, level_l, last_gauge_at | من ATG أو إدخال يدوي |
| `lane` | id, station, kind(truck/car), pump_id, status | 4 + 2 في النموذج |
| `fleet` | id, name, credit_limit, wallet_balance, contract_tier | B2B |
| `vehicle` | plate_norm, fleet_id?, kind, daily_quota_l | `plate_norm` = مفتاح منع الازدواج |
| `booking` | id, plate_norm, product_id, liters, slot_start/end, state, price_ref, qr_nonce, border_ref?, created_at | الحالة: `booked → called → fueling → done / cancelled / expired` |
| `transaction` | id, booking_id, actual_l, amount, payment_method, pump_counter_before/after, at | يُولَّد من حدث التعبئة فقط |
| `supply_order` | id, station, product, requested_l, state, approved_at, **valid_until (72h)**, eta, tanker_ref | تتبّع الصهريج |
| `ledger_entry` | id, account, debit/credit, ref, at | دفتر الأستاذ (double-entry مبسّط) |
| `event` | id, aggregate, type, payload, actor, at, hash | **append-only**، سلسلة تجزئة للتحقق |

**قيود سلامة إلزامية:**
- حجز نشط واحد لكل `plate_norm` في النافذة الزمنية.
- `SUM(booked_liters in slot) ≤ tank.level_l + confirmed_inbound_l − safety_buffer`.
-QR ذو استخدام واحد (`qr_nonce`) + انتهاء صلاحية + ربط بـ `lane`.
- لا تُصدر `transaction` إلا بـ `pump_counter_after > before`.

## 4. واجهة API (كما نُفّذت في النموذج)

| الطريقة | المسار | الوظيفة |
|---|---|---|
| `GET` | `/api/health` | فحص الجاهزية |
| `GET` | `/api/state` | لقطة كاملة للتشغيل (أسعار، خزانات، مسارات، طابور، حجوزات، أساطيل، توريد، مؤشرات) |
| `POST` | `/api/bookings` | إنشاء حجز باللوحة، يتحقق من الحصة والسعر واللوحة المكررة |
| `POST` | `/api/bookings/{id}/call` | استدعاء التالي وتخصيص مسار |
| `POST` | `/api/bookings/{id}/start` | بدء التعبئة ( QR يُستهلك ) |
| `POST` | `/api/bookings/{id}/complete` | إتمام: خصم الخزان + إنشاء معاملة + خصم المحفظة + حدث |
| `POST` | `/api/bookings/{id}/cancel` | إلغاء مع السبب |
| `POST` | `/api/prices` | تحديث نشرة السعر (صلاحية مشغّل/مدير) |
| `POST` | `/api/tanks/{product}/refill` | تسجيل وصول صهريج |
| `POST` | `/api/supply-orders` | توليد/تحديث أمر توريد مع مؤقت 72 ساعة |
| `POST` | `/api/tick` | تقدّم المحاكاة: وصول مركبات، تقدّم الحالات، تحديث المؤشرات |
| `POST` | `/api/reset` | إعادة بيانات العرض |

كل طلبات الكتابة تقبل `Idempotency-Key` في الإنتاج؛ في النموذج يُكتفى بفحص الحالة على الخادم (state machine) لمنع الانتقالات الخاطئة.

## 5. محرك الحصص (QuotaEngine) — قلب الفكرة

```
available(slot) =
      tank_level(product)
    + Σ supply_order.confirmed_l (واصل قبل slot_start)
    − Σ booking.liters (كل الحجوزات المحجوزة حتى slot_end)
    − safety_buffer (مثلاً 8% من سعة الخزان)

if requested_l > available → اعرض: «كمية جزئية» أو «أقرب نافذة بديلة» (لا ترفض بصمت)
if price_bulletin.expired → أعد التسعير وأطلب تأكيد السائق
if plate has active booking → رفض + رابط للحجز القائم
```

هذا هو الفرق الجوهري عن أي «تطبيق طابور»: **المنصة لا تعد إلا بما تستطيع الوفاء به**.

## 6. الاختيار التقني المقترح للإنتاج

| الطبقة | المرحلة 1 (سريع) | الإنتاج |
|---|---|---|
| الخلفية | Python stdlib (هذا النموذج) | FastAPI أو NestJS + PostgreSQL + Redis |
| الواجهات | Vanilla JS + RTL CSS (هذا النموذج) | Next.js/React PWA، نفس تصميم RTL، دعم تركي |
| الطابور/الأقفال | قفل ملف + state machine | Redis + أقفال موزعة + Kafka/NATS للأحداث |
| الأجهزة | إدخال يدوي لمستوى الخزان | ATG عبر RS-485/MQTT، طابعة حرارية، ANPR، شاشة مسار |
| الدفع | نقد + محفظة تجريبية | حوالات/محافظ محلية + تسوية متعددة العملات + فاتورة إلكترونية |
| الإشعارات | داخل الواجهة | SMS + واتساب + USSD (للسائقين بلا هواتف ذكية) |
| الاستضافة | محلي في المحطة (edge box) | سحابة + **وضع offline عند انقطاع الشبكة** مع مزامنة لاحقة |

> **قرار تصميمي مهم:** المحطة يجب أن تعمل حتى لو انقطع الإنترنت عند الحدود. لذلك توجد نسخة `edge` محلية تُشغّل الطابور والمضخات وتُزامن الدفتر عند عودة الاتصال.

## 7. الأمان والحوكمة

- **RBAC**: سائق / مشغّل / مدير محطة / محاسبة / هيئة المنافذ (قراءة مجمّعة فقط).
- **سجل أحداث append-only** بسلسلة تجزئة + توقيع زمني → أي تعديل على كمية أو سعر يظهر في التسوية.
- **مطابقة يومية ثلاثية**: عدّاد المضخة ↔ مستوى الخزان ↔ الفواتير؛ الفرق > 0.3% يوقف التسوية ويفتح تنبيهاً.
- **منع التحايل**: حصة يومية لكل لوحة، QR وحيد الاستخدام، ربط المسار بالحجز، سياج جغرافي (geofence) اختياري، كشف الحجوزات المتكررة بلا حضور (no-show scoring).
- **الخصوصية**: أقل قدر من البيانات الشخصية، بيانات الهيئة مجمّعة ومجهولة، فصل بيانات الدفع عن بيانات الحركة، موافقة صريحة على الإشعارات.

## 8. خارطة التنفيذ التقنية (Sprints)

| Sprint | المخرج القابل للقياس | Depend-on |
|---|---|---|
| S1 | state machine للحجز + QR + لوحة المسارات (موجود في النموذج) | — |
| S2 | PostgreSQL + RBAC + سجل الأحداث + تسوية وردية | S1 |
| S3 | ATG/عدّادات + طابعة تذاكر + وضع offline | S2 |
| S4 | `SupplyAdapter` (CSV/RPA) + مؤقت صلاحية 72 ساعة + تنبيهات | S2 |
| S5 | محفظة الأسطول + دفتر الأستاذ + فاتورة + بوابة الشركات | S2 |
| S6 | `BorderAdapter` + مزامنة مواعيد العبور + توقّع الطلب | S4, S5 |
| S7 | تعدد المحطات «ممر OS»: عزل بيانات كل منفذ + بطاقة وقود مشتركة | S6 |
| S8 | لوحة الهيئة + Warehouse + توقّع الذروة | S7 |

**Definition of Done لكل Sprint:** اختبار من الطرف إلى الطرف على 20 شاحنة حقيقية في المسار المخصص + مطابقة يومية صفر الفروق.

## 9. أسئلة مفتوحة تحتاج قرار المالك

1. هل يوجد واجهة/تصريح للوصول إلى **منصة التوريد المعتمدة** أم نبدأ بالمسار شبه اليدوي؟
2. هل يمكن ربط **موعد العبور الجمركي** برقم اللوحة (ولو عبر ملف يومي من إدارة المنفذ)؟
3. من يملك عقد التوريد: الكازية مباشرة أم عبر شركة توزيع؟ (يحدد شكل `SupplyAdapter` والفاتورة).
4. العملة التعاقدية لعقود الأساطيل (ل.س / ليرة تركية / دولار) وآلية التسوية مع الشركات التركية.
5. هل الهدف النهائي **تشغيل كازية واحدة بكفاءة أعلى** أم **ترخيص المنصة لشبكة منافذ**؟ (الخيار الثاني هو ما يوصي به هذا التصميم).
